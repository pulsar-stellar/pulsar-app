# Glossary: pulsar-app

Terms a fresh session needs in order to read this repo. One paragraph each, ordered from the ledger outward to the app.

## Ledger

A single block in Stellar's chain. Ledgers close roughly every five seconds and each one carries the transactions applied in that interval. A ledger number is the ordering key for everything historical in this repo: events are fetched from a starting ledger, stored with the ledger they appeared in, and paged through in ledger order.

## XDR

External Data Representation, the binary encoding Stellar uses on the wire and in the ledger. Every value crossing the protocol boundary is XDR-encoded, which is why raw event data is unreadable without decoding. Turning XDR into something a developer can use is the problem this toolkit exists to solve.

## SCVal

Smart Contract Value, the union type that represents any value a Soroban contract can hold or emit. An `ScVal` may be an integer, a boolean, a symbol, a string, an address, a vector, a map, or several other variants. Every event topic and every event payload is one. Decoding an event means walking `ScVal` variants and producing typed data.

## Contract event

A structured record a Soroban contract emits during execution, deliberately, as part of its interface. It carries topics, which are indexed and filterable, and data, which is the payload. Contract events are the subject of this entire toolkit: what the indexer collects, what the SDK returns, and what the explorer displays.

## Diagnostic event

An event the host emits for debugging rather than as part of a contract's interface. Diagnostic events are not guaranteed to be present, since RPC nodes can be configured not to record them, and their shape is not a stability commitment. Do not build features on them.

## TTL

Time To Live, the ledger count after which a Soroban storage entry expires and stops being readable. Entries must be extended before that happens or the data becomes unreachable. It matters here because a contract whose state has expired can still have a full event history in the indexer, so the explorer may show events for state that no longer exists on the ledger.

## Soroban RPC

The JSON-RPC service that serves Soroban contract data: simulating transactions, submitting them, reading contract state, and querying events. It is the only interface the indexer speaks to the network through. Distinct from Horizon.

## Horizon

Stellar's older REST API, covering classic Stellar operations such as payments, accounts, and offers. It does not serve Soroban contract events. Named here so nobody reaches for it by reflex; this repo does not use it.

## getEvents

The Soroban RPC method that returns contract events matching a filter, from a starting ledger, with a cursor for paging. It is the indexer's only source of event data. Its critical limitation is retention: an RPC node keeps only a recent window of history, commonly around seven days, and everything older is gone from RPC permanently. Storing events before they age out of that window is the reason the indexer exists.

## RPC endpoint

The URL of a Soroban RPC node. Configured as `PULSAR_INDEXER_RPC_URL` for the indexer and passed into the SDK for direct reads. Public endpoints exist for testnet and are rate limited and best effort, so a production indexer should point at a dedicated provider.

## Testnet

The public Stellar test network. It carries no value, and it is periodically reset, wiping all state and history. Everything in this project targets testnet until v1.0.

## Futurenet

A separate network running pre-release protocol versions, used for testing features before they reach testnet. Not used by this project, listed so the distinction from testnet is clear.

## Mainnet

The public Stellar network carrying real value. Nothing in this repo is deployed against it, and no code here should be run against it while the audit status in SECURITY.md says unaudited.

## Indexer

The Go daemon in `indexer/`. Polls `getEvents` on an interval for the contracts it tracks, decodes what it gets, validates it, stores it in SQLite or Postgres, and serves it over an HTTP read API. It is the component that makes event history outlive the RPC retention window.

## SDK client

`PulsarClient` in `packages/sdk`, the TypeScript entry point. Wraps the indexer's HTTP API in typed methods, validates every response with Zod before returning it, and throws typed `PulsarError` subclasses on failure. It also offers a direct-RPC path for a caller who wants live events and is not running an indexer.

## Contract client, generated

Typed bindings generated from a deployed contract's interface, giving a caller one method per contract function with real argument and return types. Generated by tooling rather than written by hand. This repo does not generate them for consumers; the SDK's `contract.ts` provides helpers that operate on bindings a consumer generated themselves. The exact generation command is being verified. See ADR-011.

## Migration

A numbered, ordered SQL file that moves the indexer's database schema from one version to the next. Migrations are embedded in the binary and applied at startup, so a deploy carries its own schema changes. Every migration must be valid on both SQLite and Postgres, per ADR-003.

## pgx

The Postgres driver the indexer uses in production. Chosen over `database/sql` with a generic driver for its native Postgres protocol support and its typed parameter handling, which is what keeps queries parameterized rather than concatenated.

## chi middleware

A `func(http.Handler) http.Handler` wrapper in the indexer's HTTP stack. Because chi keeps handlers as standard `http.Handler` values, middleware composes without adapters and each layer, request logging, panic recovery, request IDs, rate limiting, can be tested on its own. See ADR-007.

## App Router

The Next.js routing model where the file tree under `app/` defines routes and components are Server Components unless marked `use client`. The only routing model this repo uses. See ADR-004.

## Server Component

A React component that renders on the server and ships no JavaScript for itself to the browser. It can read data directly, without an API round trip from the client. The default for everything in `apps/web`, with `use client` added only where a component needs state, effects, or event handlers.

## TanStack Query

The client-side data fetching and caching library the explorer uses for paging and refetching against the indexer. Its `infiniteQuery` maps onto the indexer's cursor pagination directly. Initial render still comes from Server Components; Query takes over from there. See ADR-006.
